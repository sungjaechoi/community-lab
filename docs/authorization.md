# 인증·권한·데이터 공개 정책

작성일: 2026-10-26 · 대상: `01-03`~`01-05`·`01-08` · **P-01~P-08 사용자 확인·01-RECORD 완료**. 최초 검토 이력·실제 응답·기록 시각은 [확인 기록](reviews/step01.md)에 보존했다.

정책의 단일 기준은 [요구사항 P-01~P-08](requirements.md)이다. 아래는 그 정책을 역할과 접근 경로로 펼친 표다. 실제 서버·SQL·RLS 정책을 구현하거나 검증한 상태가 아니다.

## 1. 누가 무엇을 할 수 있는가

인증은 “누구인가”, 인가는 “이 대상에 이 행동을 해도 되는가”다. 로그인만으로 모든 데이터에 접근할 수 있는 것은 아니다. 화면의 버튼 표시와 서버의 허용 조건을 같은 규칙으로 맞춘다.

| 대상·행동 | 비로그인 | 로그인한 본인·당사자 | 다른 로그인 사용자 | 서버에서 확인할 조건 |
| --- | --- | --- | --- | --- |
| 공개 글·댓글 조회 | 허용 제안 | 허용 | 허용 | 삭제되지 않은 글, 삭제 댓글은 제한된 자리표시자만 반환 |
| 글·댓글 작성 | 거부 | 허용 | 자신의 내용만 작성 가능 | 유효 세션·입력, 댓글은 글/부모 소속·깊이·삭제 상태 |
| 글·댓글 수정·삭제 | 거부 | 작성자만 허용 | 거부 | 저장 시 작성자 ID 조건 유지, 삭제 상태 확인 |
| 친구 요청 | 거부 | 상대에게 요청 가능 | 다른 사람을 사칭해 요청 불가 | 요청자는 세션에서 결정, 대상 유효·자기 아님·친구/pending/대기시간 검사 |
| 받은/보낸 요청 조회 | 거부 | 자신의 요청만 허용 | 타인의 요청 목록 거부 | 요청자 또는 수신자가 현재 사용자 |
| 요청 수락·거절 | 거부 | 해당 pending 수신자만 | 요청자·제3자 거부 | 요청 ID·수신자·현재 상태, 원자적 수락 |
| 친구 목록 조회·관계 삭제 | 거부 | 본인 목록·본인 포함 관계만 | 타인의 목록/관계 거부 | 현재 사용자가 관계 당사자 |
| 쪽지 발송 | 거부 | 현재 친구에게만 | 타인의 발신자 ID 사용 불가 | 발신자는 세션에서 결정, 대상·현재 친구 여부·전송 키 |
| 쪽지 목록·상세 | 거부 | 발신자/수신자이며 자신의 삭제 표시가 없는 경우 | 제3자 거부 | 당사자 조건과 개인별 삭제 조건 모두 적용 |
| 쪽지 읽음 변경 | 거부 | 수신자만 | 발신자·제3자 거부 | 수신자 본인, 본인함에서 삭제되지 않은 쪽지 |
| 쪽지 개인별 삭제 | 거부 | 자기 수신/발신함에서만 | 상대의 삭제 상태 변경 불가 | 본인 쪽 삭제 표시만 변경, 상대 기록 보존 |
| 새 1대1 방 생성 | 거부 | 현재 친구 쌍만 | 타인 두 명의 방 생성 불가 | 세션 사용자를 참여자로 고정, 쌍당 방 하나 |
| 기존 방·메시지 이력 조회 | 거부 | 두 참여자 허용 | 친구여도 비참여자는 거부 | 방 참여자 조건. 친구 삭제 후에도 조회 허용 제안 |
| 채팅 메시지 전송 | 거부 | 참여자이며 현재 친구일 때만 | 비참여자 거부 | 방 참여자·현재 친구 여부·본문·재시도 키 |
| private Realtime 수신 | 거부 | 인증된 해당 방 참여자만 | 비참여자 거부 | private 채널과 별도 수신 정책, topic에 해당하는 방 참여자 |

메뉴를 숨겨도 직접 URL/API 요청은 가능하므로 서버 검사는 항상 수행한다. 인증된 사용자 ID·작성자·발신자를 요청 본문으로 지정하게 하지 않는다. 대상 ID가 공개되어도 접근 권한은 생기지 않는다.

친구 요청의 pending 조건은 실제 상태 변경에 적용한다. 같은 수신자의 동일 수락·거절 재시도는 [요구사항 4.2](requirements.md)의 기존 결과 반환 규칙을 따르며, 친구 삭제 뒤 과거 accepted 재수락은 409로 거부한다.

## 2. 공개 응답과 오류 규칙 제안

| 상황 | 응답 초안 | 이유·UI 동작 |
| --- | --- | --- |
| 형식·타입·빈 본문·초과 길이·잘못된 부모 | 400 + 안전한 필드 오류 | 입력 옆 안내, 작성 내용 보존 |
| 보호 요청의 세션 없음·만료 | 401 | 로그인 유도. 실제 인증 여부를 서버에서 확인 |
| 공개 글/댓글의 타인 변경, 수신자가 아닌 사람의 요청 처리·읽음 변경 | 403 | 공개 대상의 존재를 숨길 필요가 없는 범위에서 행동 권한 없음 안내 |
| 없는 대상·삭제된 글 | 404 | 찾을 수 없거나 이용할 수 없는 화면 |
| 비공개 쪽지/방의 제3자 직접 접근, 본인이 숨긴 쪽지, 타인 친구 관계 | 404 | 데이터 존재 여부를 추가로 노출하지 않음 |
| 이미 처리된 요청·재요청 대기·관계 변경·같은 전송 키에 다른 내용 | 409 | 현재 상태를 갱신하고 다시 할 수 있는 행동 안내 |
| 내부 저장·네트워크 실패 | 안전한 5xx/실패 응답 | DB 오류 전문·연결 정보 대신 재시도 안내, 실패한 변경은 성공으로 표시하지 않음 |

위 표의 수신자 전용 읽음 변경 403은 발신자처럼 이미 쪽지에 접근할 수 있는 사람에게 적용한다. 제3자는 읽음 변경도 404로 처리한다. 비로그인은 비공개 대상 존재를 조회하기 전에 401로 거부한다. 세부 오류 코드·응답 모양은 각 API 계약에서 확정한다.

공개 작성자 정보는 사용자 ID와 닉네임으로 제한한다. 이메일·Auth 원본 프로필·토큰·세션·DB 자격 증명은 반환하지 않는다. 삭제 댓글의 원문·작성자 정보도 반환하지 않는다. 쪽지·채팅 목록/본문을 공용 캐시나 비로그인 화면에 섞지 않는다.

## 3. 서버·Data API·Realtime은 다른 접근 경로다

| 경로 | 기본안·책임 | 후속 검증 |
| --- | --- | --- |
| 브라우저 → Next.js API → Drizzle → PostgreSQL | 업무 데이터 조회·변경은 이 경로. 서버가 세션·입력·대상 권한을 검사한다. DB 연결 역할이 사용자 JWT를 자동으로 전달받는다고 가정하지 않는다 | A/B/C 요청·조건부 변경·DB 제약, 런타임 DB 역할과 실제 RLS 동작 |
| 브라우저 → Supabase Auth | Google 로그인·세션 용도. 로그인 결과를 업무 데이터 권한으로 그대로 확대하지 않음 | callback·세션 만료·로그아웃·복귀 URL 검사 |
| 브라우저 → Supabase Data API | 앱 업무 테이블의 직접 접근은 기본 금지 제안. 테이블 생성 때 필요한 권한 회수·RLS를 함께 적용 | anon/authenticated로 posts·쪽지·채팅을 직접 요청해 우회가 차단되는지 검사 |
| 브라우저 → private Realtime | 참여자만 방 이벤트를 수신. 메시지 작성은 HTTP API로 저장 후 DB trigger가 전달 | A·B 수신, C와 비로그인의 구독 거부, 공개 topic 우회·재연결·로그아웃 검사 |

RLS는 DB의 행 단위 접근 정책이고 GRANT/REVOKE는 DB 객체에 대한 권한 허용/회수다. 직접 DB 연결의 역할이 테이블 소유자이거나 RLS 우회 권한을 가진 경우까지 조사해야 한다. “RLS를 켰으니 서버 검사가 필요 없다”거나 “private 설정만 했으니 안전하다”로 완료 처리하지 않는다. 상세 기술 근거는 [기술 선택 초안](decisions/0001-tech-stack.md)에 있다.

친구 삭제 후 기록 조회 권한은 유지하는 제안이므로 기존 방의 수신 자격을 즉시 철회하는 기능을 요구하지 않는다. 새 전송 차단은 저장 API에서 관계를 다시 확인한다. 탈퇴·차단처럼 참여권 자체를 회수하는 기능은 별도 설계가 필요하고, 이번 범위에서 즉시 회수 검증까지 했다고 주장하지 않는다.

## 4. 실제로 확인할 권한 사례

| 사례 | 기대 API·DB 결과 | 기대 화면·연결 결과 | 관련 기준 |
| --- | --- | --- | --- |
| 비로그인 공개 조회 후 작성 시도 | 조회 허용, 작성 401·DB 불변 | 글은 보이고 로그인 안내 | AC-AUTH-03·AC-POST-03 |
| B가 A의 글·댓글 변경 | 403·원문 불변 | 본인 버튼 없음, 직접 URL/API도 거부 | AC-POST-03·AC-COMMENT-03 |
| A/C가 B에게 온 요청 수락 | 403·요청/관계 불변 | B만 처리 버튼, 오류 후 새 상태 조회 | AC-FRIEND-03 |
| C가 A→B 쪽지 상세·삭제·읽음 요청 | 404·내용/읽음/삭제 상태 불변 | 내용을 보여 주지 않는 접근 불가 안내 | AC-INBOX-03 |
| A가 자신의 발신 쪽지를 읽음 처리 | 403·읽음 불변 | 읽음 변경 버튼 없음 | AC-INBOX-03 |
| A의 개인 삭제 후 B 조회 | A는 404, B는 기존 기록 조회 | A의 함에서만 사라짐 | AC-INBOX-01·04 |
| C가 A·B 방의 이력·전송·구독 접근 | HTTP 404·저장 없음·private 구독 거부 | 다른 방/이벤트가 섞이지 않음 | AC-CHAT-03 |
| A가 B와 친구 삭제 후 기록 조회·발송 | 기존 기록 허용, 새 발송 409·저장 없음 | 기록과 친구 아님 안내·전송 제한 | AC-INBOX-02·AC-CHAT-02 |
| 공개 키/로그인 세션으로 Data API 직접 접근 | 업무 테이블 직접 조회·변경 거부 | 제품 UI의 API 경로만 사용 | AC-CHAT-03·공통 비기능 기준 |

이는 후속 구현 때의 검증 계획이다. STEP 01 검토 당시 실제 세션·DB·API·Realtime은 없었고 모든 런타임 사례는 미검증이었다. 정책의 사용자 확인과 `01-RECORD`는 [01-REVIEW 기록](reviews/step01.md)에 완료했으며, 실제 구현·검증의 현재 상태는 [진행 기록](work-status.md)에서 관리한다.
