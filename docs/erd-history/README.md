# 기능별 ERD 변경 기록 기준

WHY: 마지막 그림뿐 아니라 **왜 구조를 바꿨고 무엇을 실제로 적용했는지** 다시 읽기 위해 기록한다. 현재 구조는 [erd.md](../erd.md), 읽기 예제와 원칙은 [설계 기준](../decisions/0002-database-design.md)을 따른다.

현재는 업무 테이블이 없어 기능별 변경 파일을 만들지 않았다. 해당 기능을 시작할 때 `docs/erd-history/<기능>.md`를 추가한다. 새로 생기는 API 작업 ID·schema·migration·검증을 연결하고 기존 API REVIEW에 포함한다.

## 한 기능에서 지킬 순서

1. **사용자 행동·행 예시**: 어떤 동작을 저장하려는지와 한 행의 의미를 짧게 적는다.
2. **변경 전 실제 상태**: 직전 현재 ERD를 문서에 보존하고 조회 시각·대상 환경·관련 migration을 적는다. Git의 직전 버전만 링크하는 것으로 그림을 생략하지 않는다.
3. **후보와 WHY**: 추가/변경/삭제 컬럼, 자료형·NULL·기본값·PK/FK·UNIQUE/CHECK·삭제 정책을 이유와 함께 설명한다. 후보에는 미적용 표시를 붙인다.
4. **SQL 검토**: Drizzle schema와 실제 migration 경로·SQL을 연결하고 생성/변경과 필요한 초기 GRANT·REVOKE·RLS를 함께 검토한다. 파일 생성만으로 DB 적용을 완료했다고 기록하지 않는다.
5. **분리 적용·검증**: 먼저 분리 테스트 환경에 적용해 정상·거부·제약·필요한 트랜잭션/동시성·migration 재현을 확인한다. 실제 실행 명령·기대/실제 결과·미실행 범위를 적는다.
6. **개발 적용·현재 구조**: 분리 검증을 마친 SQL을 의도한 개발 대상에 적용하고 실제 구조를 재확인한다. 성공한 구조만 현재 ERD에 반영하고 이력 파일에도 적용 후 그림을 남긴다. 환경별 적용 결과를 구분하고 실패한 적용을 완료 그림에 넣지 않는다.
7. **사용자 확인·기록**: 해당 기능의 기존 API REVIEW에서 설계 변화·SQL·API 결과를 함께 제시한다. 확인 전 REVIEW를 DONE으로 올리지 않는다.

## 파일에 남길 항목

| 항목 | 내용 |
| --- | --- |
| 기능·작업 ID·기록 시각 | 실제 해당 API ID, 검토/적용/검증 시각 구분 |
| 환경·변경 전 그림 | 개발/테스트 식별, 실제 이전 구조·근거. 비밀·사용자 데이터 없음 |
| 사용자 행동·행 예시 | 실제 저장 필요와 행의 의미. 예시는 가상 데이터로 표시 |
| 설계 후보·WHY | 전후 차이·관계·제약의 이유와 대안. 미적용 상태 표시 |
| 구현·SQL | schema·migration 실제 파일 경로와 검토할 SQL |
| 기존 데이터·호환성 | 기존 행 유무, 보정/이행 필요성, 이전 코드와의 영향 |
| 실제 적용 결과 | 성공/실패·대상·순서. 적용된 migration 보존, 수정은 후속 migration |
| 검사 근거 | 실행/미실행·정상/실패/권한/무결성/필요한 동시성·재현 결과 |
| 적용 후 그림 | 성공한 현재 상태. 현재 erd.md와 일치 |
| REVIEW·COMMIT | 사용자 실제 확인 범위·말·기록 시각, 성공 후 실제 해시 |

미래 파일 경로를 링크나 빈 문서로 미리 만들지 않는다. 적용 전 후보가 바뀌면 검토 과정을 남기고, 이미 적용한 SQL·과거 그림을 새 설계로 덮어쓰지 않는다. 실패 시 DB의 실제 남은 상태를 다시 조사하고 원인·복구/보완·재검증을 기록한다.

예를 들어 “컬럼 파일 작성”은 아직 적용 전, “migration 적용 성공”은 실제 구조 변경, “분리 테스트 통과”는 해당 검사 범위의 근거다. 이 세 가지와 사용자의 이해·REVIEW 승인은 각각 구분한다.
