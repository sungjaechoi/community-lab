# 플랜 개정 3 · 기능별 테이블 설계와 ERD 변화 학습

상태: 플랜·지침 반영 DONE · 1차 변경 기록 시각: 2026-10-26 16:59:26 +09:00 (Asia/Seoul)

## 요청과 목적

사용자의 실제 요청:

> 플랜 구조에 변경이 필요 할것 같아
> 지금은 학습하면서 프로젝트를 만드는 목적성이 강하니 한번에  ERD를 만드는게 아니라
> 각 기능을 만들때 테이블을 생상하고 그에따라서 ERD가 변경되어야
> 내가 테이블 구조가 어떻게 변경되고 어떻게 추가되고 설계가 어떤식으로 변하는지 학습이 가능할것 같아

사용자 메시지의 정확한 전송 시각은 별도 제공되지 않았다. 위 시각은 변경을 기록한 시각이다. 이 요청은 학습·설계 순서의 변경이며 현재 공통 UI 결과의 승인이 아니다.

기존에는 STEP 04에서 필수 업무 테이블 8개의 관계·제약을 미리 설계하고 STEP 05에서 profiles·posts를 먼저 생성했다. 변경 후에는 **필요한 기능을 구현할 때 데이터 문제를 만나고, 그때 설계·생성·수정한 이유를 ERD 변화로 확인**한다. 기능·정책 P-01~P-08, 기본 기술, API/UI 사용자 확인·커밋 순서는 유지한다.

STEP 04·05는 짧은 준비 범위다. 전체 기능의 컬럼·제약·SQL을 선작성하는 단계로 사용하지 않는다. 이 표는 시점을 정하는 계획이며 실제 테이블·ERD를 만든 결과가 아니다.

## 각 기능에서 보여 줄 것

1. 사용자의 행동과 간단한 데이터 행 예시에서 필요한 저장 정보를 찾는다.
2. 현재 ERD를 변경 전 스냅샷으로 보존하고, 추가·변경·삭제할 컬럼과 관계를 후보 그림으로 설명한다.
3. 자료형·NULL·기본값·PK/FK·UNIQUE/CHECK·삭제 정책이 왜 필요한지, 어떤 잘못된 입력을 막는지 설명한다.
4. Drizzle schema와 생성/직접 작성 SQL을 읽고, 초기 권한·RLS와 함께 적용한다. 기존 행을 바꾸면 호환성과 데이터 처리도 설명한다.
5. 분리된 환경에서 적용·재적용·정상/거부·제약·필요한 동시성을 확인한다. 검증하지 못한 부분은 남긴다.
6. 성공한 실제 구조만 docs/erd.md에 반영하고, docs/erd-history/<기능>.md에 전후·WHY·migration·검증을 연결한다.
7. 기존 기능 API REVIEW에서 데이터 변경과 API 결과를 함께 확인한다. 별도 DATA 승인 묶음은 추가하지 않는다.

이미 적용한 migration과 이전 ERD 스냅샷은 보존한다. 설계 후보·DB에 적용한 결과·검증 결과를 구분해, 완성된 그림뿐 아니라 구조가 바뀐 과정도 읽을 수 있게 한다.
