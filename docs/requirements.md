## 1. 목적과 이번 단계의 결과

**서비스 목적:** Google로 로그인한 사용자가 공개 글과 댓글로 교류하고, 친구를 맺어 쪽지와 1대1 채팅으로 대화하는 커뮤니티를 만든다.

## 3. 사용자와 시나리오

| 역할 | 의미 |
| --- | --- |
| 비로그인 | 세션이 없는 방문자. 제안상 공개 글·댓글만 조회 |
| 로그인 사용자 | Google 인증을 마치고 유효한 서버 확인 세션이 있는 사용자 |
| 작성자 | 현재 글·댓글을 작성한 본인. 다른 글의 작성 권한까지 얻지는 않음 |
| 요청 수신자 | 현재 친구 요청을 받은 사람. 해당 pending 요청만 수락·거절 |
| 쪽지 발신자·수신자 | 해당 쪽지의 당사자. 수신자만 읽음 상태 변경 |
| 채팅 참여자 | 해당 1대1 방의 두 사람. 타인의 방은 친구여도 접근 불가 |

검증용 A·B·C는 서로 다른 사용자다. A와 B의 대화에 C가 접근하지 못해야 한다. 한 사용자는 대상에 따라 작성자·수신자·참여자 역할을 동시에 가질 수 있다.

| 요구사항 ID | 시작 화면 → 입력·행동 → 완료 후 화면 |
| --- | --- |
| R-AUTH-01 | 공개 목록 또는 로그인 → Google 로그인 → 안전하게 검증된 앱 내부 원래 화면(없으면 글 목록). 로그아웃 → 공개 목록 |
| R-POST-01 | 글 목록 → 로그인 후 작성 → 새 글 상세. 상세 → 본인 수정 → 같은 상세. 본인 삭제 확인 → 목록 |
| R-COMMENT-01 | 글 상세 → 댓글 작성 → 해당 위치 갱신. 부모의 답글 버튼 → 답글 작성 → 부모 아래 표시. 본인 수정·삭제 → 같은 상세 |
| R-FRIEND-01 | 글 상세 작성자 버튼 → 친구 요청 → 보낸 요청 탭. B의 받은 요청 → 수락/거절 → 요청·친구 목록 갱신. 친구 삭제 → 목록 갱신 |
| R-INBOX-01 | 친구 행의 쪽지 또는 작성 화면의 친구 선택 → 발송 → 발신 상세. B의 수신함 → 상세 → 읽음. 본인함에서 삭제 → 해당 함 |
| R-CHAT-01 | 친구 행의 대화 시작 또는 빈 채팅 목록의 친구 목록 링크 → 방 생성/기존 방 반환 → 대화. 메시지 전송 → 저장 결과와 상대 화면 반영 |
| R-UI-01 | 공통 메뉴 → 현재 위치 표시, 로그인 필요 시 복귀 경로 제공. 오류 → 입력/화면 상태 유지 → 재시도 |

쪽지는 한 건 단위의 비실시간 편지이고, 채팅은 같은 방에서 이어지는 실시간 대화다. Google 표시 이름을 최초 닉네임으로 쓰는 안이며 공개 응답은 공개 사용자 ID·닉네임으로 제한한다. 이메일·세션·토큰은 공개하지 않는다. 닉네임은 고유 식별자가 아니며 빈 이름은 일반 대체 표시를 쓴다.

### 4.1 글·댓글·사용자 삭제의 구체적인 결과

- 글 수정·삭제는 작성자만 허용한다. 삭제 성공 이후 글 상세는 404, 목록에서도 제외된다. 글과 하위 댓글 제거가 함께 성공하거나 함께 실패해야 한다.
- 댓글 삭제는 논리 삭제(행의 관계는 두고 내용을 제거하는 방식)로 제안한다. 답글 유무와 관계없이 “삭제된 댓글입니다”를 표시하고 원문·작성자를 응답에서 제외한다. 수정·답글·재삭제 버튼은 제공하지 않는다. 같은 작성자의 반복 삭제는 성공 상태를 유지하되 원문을 복구하지 않는다.
- 최상위 댓글 깊이는 0, 그 댓글의 답글 깊이는 1이다. 답글을 부모로 삼거나 다른 글의 댓글을 부모로 삼는 입력은 거부한다. 삭제된 부모에 답글 작성 중 삭제가 먼저 확정되었다면 작성은 충돌로 실패하고 입력을 보존한다.
- 댓글 수는 삭제된 자리표시자를 제외한 살아 있는 댓글·답글 수로 제안한다. 부모가 삭제되어도 남아 있는 답글은 센다.
- 탈퇴는 지금 실행 가능한 기능이 아니다. 후속 ERD에서는 Auth 사용자 삭제에 의한 자동 연쇄 삭제를 무심코 적용하지 않고, 공개 내용 제거·익명 프로필과 비공개 기록의 참조 유지 가능성을 검토한다. 실제 탈퇴 작업·보관 기간·세션 무효화·정리 절차는 별도 설계와 확인이 선행되어야 하며, 이번 초안으로 탈퇴 기능을 완료 처리하지 않는다.

### 4.2 친구 상태 전이와 반복·동시 요청

| 현재 상태 | 행동 | 결과·서버 판단 |
| --- | --- | --- |
| 요청/친구 없음 | A→B 요청 | pending 요청 하나 생성. 비활성/없는 대상·자기 요청 거부 |
| A→B pending | 같은 방향 재요청 | 409 충돌, 새 요청 없음. 기존 보낸 요청으로 안내 |
| A→B pending | B→A 요청 | 409 충돌, 자동 수락 없음. B의 받은 요청으로 안내 |
| pending | B 수락 | accepted 전이와 친구 쌍 생성이 하나의 트랜잭션(전부 성공하거나 전부 취소) |
| pending | B 거절 | rejected로 전이, 친구 생성 없음. 거절 시각부터 24시간 대기 |
| pending | A 또는 C가 수락/거절 | 403 거부, 상태 불변 |
| rejected + 24시간 전 | 어느 방향의 새 요청 | 409, 남은 대기 안내, 새 행 없음 |
| rejected + 24시간 경과 | 어느 방향의 새 요청 | 과거 기록과 별도의 새 ID로 pending 하나 생성 |
| accepted + 현재 친구 | 같은 요청 재수락 | 기존 성공 결과 반환, 관계는 하나. 다시 요청하면 409 |
| rejected | 수신자의 같은 거절 재시도 | 기존 rejected 결과 반환, 거절 시각을 다시 늦추지 않음 |
| accepted + 친구 삭제됨 | 과거 요청 재수락 | 409, 관계 복원 금지. 새 요청과 수락 필요 |
| rejected 또는 accepted | 반대 결정으로 변경 | 409, 닫힌 요청을 되돌리지 않음 |
| 현재 친구 | 당사자가 친구 삭제 | 관계 제거. 기존 쪽지·방·메시지는 P-05대로 유지 |
| 이미 삭제한 관계 | 당사자의 반복 삭제 | 삭제된 상태 유지. 제3자는 관계 존재를 노출하지 않는 404 |

두 방향이 동시에 요청해도 활성 pending은 쌍당 하나다. 같은 수락이 동시에 실행되어도 친구 관계는 하나이며 중간 DB 실패 시 accepted만 남지 않아야 한다. 친구 삭제·발송이 겹치면 서버가 동일 쌍의 변경 순서를 일관되게 적용한다. 발송이 먼저 확정되었으면 그 메시지는 남고, 삭제가 먼저 확정되었으면 새 발송은 거부한다. 구체적인 잠금·제약 방식은 STEP 04·10에서 설계·검증한다.

### 4.3 쪽지·채팅 접근과 전송

- 쪽지는 친구 목록에서 수신자를 선택한다. URL의 recipientId만 믿지 않고 발송 시 서버가 현재 관계·대상을 확인한다. 발신자는 수정·회수할 수 없다.
- 쪽지 읽음은 수신자가 상세를 성공적으로 열었을 때 수신자 전용 변경 요청으로 기록한다. 발신자가 상세를 보거나 목록 미리보기를 보는 것만으로 읽음 처리하지 않는다. 발신함에서 읽음 여부를 확인할 수 있다.
- 개인별 삭제는 내 수신/발신함과 상세에서만 숨긴다. 상대 기록은 유지하며, 내가 삭제한 쪽지를 직접 ID로 요청해도 404다. 한쪽 삭제가 다른 쪽의 읽음 여부·접근을 바꾸지 않는다.
- 새 쪽지 제출의 연속 클릭은 처리 중 버튼으로 막는다. 서버 중복 처리는 API 계약 단계에서 요청 키를 정해 같은 전송 재시도는 기존 성공 결과, 같은 키·다른 수신자/본문은 409로 제안한다. 쪽지 응답 유실 후 중복 발송도 검증 대상으로 둔다.
- 1대1 방은 사용자 쌍당 하나다. 같은 쌍이 동시에 방을 만들어도 같은 방으로 수렴한다. 사용자가 방에서 나가거나 방을 지우는 기능은 MVP 밖이다.
- 채팅은 서버 저장 성공 후 전달한다. 같은 `(방, 발신자, client_message_id)`와 같은 본문의 재전송은 기존 성공 결과를 반환한다. 같은 키·다른 본문은 409다. 새 의도의 메시지는 새 키를 사용한다.
- 화면에서는 서버 message.id로 HTTP 응답·조회 이력·중복 이벤트를 합친다. 저장 실패·전송 중·실시간 연결 중·복구 실패를 성공 상태와 구분한다.
- 친구 삭제는 방 참여자 제거가 아니다. 두 사람의 과거 기록 조회·수신 자격은 유지하며, 새 메시지 저장만 현재 친구 여부로 제한한다. 이미 저장된 메시지의 늦은 이벤트는 도착할 수 있다. 로그아웃하면 클라이언트 구독을 해제하며 세션 만료·재연결 권한도 검증한다.
- 재접속은 인증된 구독 성공 뒤 이력을 페이지 단위로 재조회·대조한다. 조회 중 이벤트도 합친다. 시간 하나만으로 완전 복구·정확히 한 번 전달을 보장하지 않으며 STEP 11에서 실제 복구 범위·비용·한계를 기록한다.

### 4.4 입력·정렬 초안

| 입력 | 정규화 뒤 허용 길이 |
| --- | --- |
| 글 제목 | 1~100자 |
| 글 본문 | 1~10,000자 |
| 댓글·답글 본문 | 1~1,000자 |
| 쪽지·채팅 본문 | 각각 1~2,000자 |

모두 일반 텍스트로 렌더링하며 HTML·마크다운 작성·첨부는 보류한다. 앞뒤 공백 제거와 줄바꿈 형식 통일 후 서버에서 길이를 센다. 글자 수는 Unicode 코드 포인트 수로 제안한다. 결합 이모지는 화면상 한 글자여도 여러 개로 셀 수 있으므로 구현 시 입력 안내와 서버 기준을 일치시킨다. 브라우저의 글자 제한만 보안 검사로 사용하지 않는다. ID 형식·본문 타입·요청 크기·허용 필드도 서버에서 검증하고 사용자 ID를 요청 본문으로 신뢰하지 않는다.

| 목록 | 정렬·조회 단위 제안 |
| --- | --- |
| 게시글·쪽지·친구 요청 | 생성 시각 내림차순 + ID 내림차순, 첫 20건·더 보기 |
| 친구 | 관계 생성 시각 내림차순 + ID 내림차순, 20건·더 보기 |
| 댓글 | 부모 생성 시각 오름차순 + ID 오름차순. 부모 20개, 답글도 부모별 20개씩 추가 조회. 삭제 부모는 관계 표시를 위해 포함 |
| 채팅방 | 마지막 저장 메시지 시각(없으면 방 생성 시각) 내림차순 + 방 ID 내림차순, 20개·더 보기 |
| 채팅 메시지 | 최신 50개를 불러와 화면에는 생성 시각·ID 오름차순 표시, 위쪽에서 이전 50개씩 조회 |

서버 시각·ID를 정렬 기준으로 삼고, 잘못된 limit/커서는 400으로 거부한다. 커서(다음 조회 위치를 나타내는 값)의 상세 구조와 상한은 각 API 계약에서 정하며, 댓글의 부모·답글이 잘리지 않는지 검증한다. STEP 13에서 실제 데이터·실행 계획으로 페이지 조회 성능과 방식도 재검토한다. API에 없는 총 페이지 수·전체 복구 완료를 UI가 임의로 표시하지 않는다.

## 5. 요구사항 → 화면 → API → 검증 연결

경로는 설계 초안이며 아직 요청할 서버 주소는 없다. 화면 ID는 [화면 문서](screens.md), 권한·오류는 [권한 문서](authorization.md)가 기준이다. 상세 요청/응답 필드·CSRF 방어(다른 사이트가 사용자의 세션으로 변경 요청을 보내는 공격 방지)·요청 키 저장 방식은 해당 API 구현 전 계약에서 확정한다. 세션 쿠키를 쓰는 변경 요청은 서버의 출처·세션 검증 등 선택한 방어를 검증한다.

| 요구사항 | 화면 ID | API 역할·경로 초안 | 수용 기준 | 구현 STEP |
| --- | --- | --- | --- | --- |
| R-AUTH-01 | S-01 및 공통 메뉴 | 로그인 시작, GET /auth/callback, POST /api/auth/logout, GET /api/me | AC-AUTH-01~04 | 06 |
| R-POST-01 | S-02~05 | GET/POST /api/posts, GET/PATCH/DELETE /api/posts/[postId] | AC-POST-01~04 | 07·08 |
| R-COMMENT-01 | S-03 | GET/POST /api/posts/[postId]/comments, GET /api/comments/[commentId]/replies, PATCH/DELETE /api/comments/[commentId] | AC-COMMENT-01~04 | 09 |
| R-FRIEND-01 | S-03·06 | GET/POST /api/friend-requests, PATCH /api/friend-requests/[requestId]（accept/reject）, GET /api/friends, DELETE /api/friends/[userId] | AC-FRIEND-01~05 | 10 |
| R-INBOX-01 | S-06~10 | GET/POST /api/inbox, GET/DELETE /api/inbox/[messageId], PATCH /api/inbox/[messageId]/read | AC-INBOX-01~04 | 10 |
| R-CHAT-01 | S-06·11·12 | GET/POST /api/conversations, GET /api/conversations/[conversationId], GET/POST /api/conversations/[conversationId]/messages + private Broadcast | AC-CHAT-01~05 | 11 |

로그인 시작은 Supabase Auth의 OAuth 흐름을 사용하고 callback에서 세션을 확립한다. 위 표가 별도의 비밀번호 로그인 API를 요구하지는 않는다. 목록의 받은/보낸 구분과 대상 선택 필터는 해당 계약에서 정의한다.

| AC-UI-02 입력·삭제 | 서버 거부 때 값이 변하지 않으며 사용자에게 안전한 오류만 노출 | 폼 라벨·필드 오류·키보드 초점, 주요 삭제 확인, 취소 복귀, 실패 시 입력 유지 |
| AC-UI-03 탐색·모바일 | 목록 정렬·조회 끝 신호·권한 필터 준수, 추가 조회 실패 뒤 재시도 | 360px와 데스크톱에서 겹침/가로 넘침 없음, 키보드 주요 흐름, 더 보기/끝 상태 |

글·댓글 생성의 응답 유실 재시도에서 서버가 중복 작성을 어떻게 다룰지는 해당 API 계약에서 정한다. UI의 클릭 방지만으로 서버의 중복 저장 방지를 검증했다고 쓰지 않는다. 친구 수락·방 생성·메시지 전송의 중복/동시성은 이번 필수 수용 기준이다.

비기능 기준: 서버 비밀값·이메일·토큰을 브라우저/공개 응답/로그/Git에 노출하지 않기, 분리 테스트 환경 사용, migration(순서대로 적용하는 DB 변경 이력)으로 제약·접근 제한 재현, 실제 API 연결과 접근성 상태 확인. 성능 목표 수치는 아직 측정하지 않았으며 STEP 13에서 근거와 함께 정한다.

## 7. 작은 예제로 보는 서버 권한 검사

아래는 흐름 설명용 의사 코드다. 실행 파일·실제 API·테스트 결과가 아니다.

```ts
const user = await verifySession();      // 인증: 누구인가?
if (!user) return error(401);
const input = validatePostInput(body);   // 입력: 제목·본문이 유효한가?
const post = await findPost(postId);
if (!post) return error(404);
if (post.authorId !== user.id) return error(403); // 인가: 이 글을 바꿔도 되는가?
return updateOwnedPost(postId, user.id, input);  // 저장 때도 작성자 조건 유지
```

입력은 수정할 글 ID와 새 내용이다. 서버는 세션·입력·대상·작성자를 확인한 뒤 본인 글만 조건부로 변경하고 결과를 반환한다. 화면에서 수정 버튼을 숨기는 것만으로는 B가 직접 보낸 요청을 막을 수 없기 때문에 저장 경로에도 검사가 필요하다.

## 8. 면접 질문·학습 상태

1. **인증과 인가는 어떻게 다른가요?** 인증은 사용자가 누구인지, 인가는 현재 대상에 행동할 수 있는지를 확인한다. 로그인한 B도 A의 글을 수정할 수 없다.
2. **왜 수용 기준을 API와 UI로 나누나요?** API는 잘못된 요청·권한·DB 결과를, UI는 실제 진입·상태·입력 보존·연결을 확인한다. 한쪽 성공만으로 전체 기능 완료를 주장할 수 없다.

설명은 제공했다. 사용자의 이해 확인·복습 완료는 아직 확인하지 않았다. [01-REVIEW](reviews/step01.md)의 정책 확인과 `01-RECORD`는 완료했으며 다음 작업 ID는 `02-ENV-01`이다.
