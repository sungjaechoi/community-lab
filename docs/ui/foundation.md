# STEP 02 공통 UI와 WHY

작성일: 2026-10-26 (Asia/Seoul) · 현재·다음 ID: **02-UI-REVIEW / WAITING_USER_REVIEW**

공통 UI 구현·검증 자료를 준비했으며 사용자 확인과 UI 커밋은 아직 없다. 환경 커밋 `d9b9f8f`와 해당 push는 완료했다. 현재 결과와 확인 절차는 [UI 검토 자료](../reviews/step02-ui.md), 전체 진행은 [진행 기록](../work-status.md)을 따른다.

## 목적과 이번 범위

목적은 이후 기능들이 같은 메뉴·입력·실패 안내를 사용하게 만드는 것이다. WHY는 기능마다 버튼과 오류 동작이 달라지는 문제를 줄이고, 서버 연결 전에 화면의 기본 사용성을 확인하기 위해서다. [승인된 화면 방향](../screens.md)을 밝은 바탕·한 가지 강조색·목록 중심으로 구현했다.

| 작업 | 구현한 결과·이유 |
| --- | --- |
| 02-UI-01 | 공통 헤더·메뉴·본문·푸터. 어디서든 같은 길로 이동 |
| 02-UI-02 | 색상·간격·버튼과 현재 메뉴 표시. 위치와 행동을 구분 |
| 02-UI-03 | 라벨·필드 오류·처리 중 버튼·확인창. 실수를 수정하고 취소할 수 있게 함 |
| 02-UI-04 | 로딩·빈 결과·오류·권한·준비 상태 요소. 다음 행동을 안내 |
| 02-UI-05 | 실제 브라우저·키보드·화면 너비·HTTP·타입·린트·빌드 검사. 결과는 아래 범위만 주장 |

`/`는 `/posts`로 이동한다. 게시글·친구·쪽지·채팅·로그인은 모두 기능 준비 화면이다. 글쓰기·Google 로그인은 준비 안내와 비활성 버튼으로 표시한다. 실제 회원·게시글 같은 가짜 업무 데이터는 넣지 않았고 새 의존성도 추가하지 않았다.

## 화면·설정의 역할

| 소스·설정 | 맡는 역할과 선택 이유 |
| --- | --- |
| `src/app/layout.tsx` | 한국어 문서·제목 규칙·헤더·본문 바로가기·푸터를 공유 |
| `src/components/app-header.tsx` | 현재 경로를 `aria-current`로 표시. 모바일 메뉴는 펼침 상태·Escape 닫기·버튼 초점 복귀 제공 |
| `src/app/globals.css` | 색상 변수·레이아웃·반응형·초점·움직임 줄이기. 생성기 Tailwind 구성을 유지하고 공통 스타일을 한곳에서 관리 |
| 본문 너비·화면 분기 | 본문 최대 1180px, 기본 좌우 32px. 760px 이하 메뉴 접기·한 열, 420px 이하 좌우 17px. 좁은 화면에서 읽을 공간 확보 |
| 색상·글꼴 | 배경 `#f7f8fc`, 흰 카드, 강조 `#4658d9`, 보조 글자 `#667085`, 시스템 글꼴. 외부 글꼴 요청 없음 |
| `loading.tsx`·`error.tsx`·`not-found.tsx` | 경로 공통 상태와 재시도·돌아가기 제공. 실제 오류 경계에 장애를 주입한 검증은 아직 없음 |

보조 글자의 흰 배경 대비를 약 **4.97:1**로 확인하고 상태 설명·입력 힌트의 낮은 대비를 보완했다. 이는 해당 조합의 검사이며 전체 디자인의 WCAG 준수를 선언하는 결과는 아니다.

## 지금 필요한 재사용 요소

| 요소 | 동작과 WHY |
| --- | --- |
| `Button` | 기본·보조·위험·간단 버튼, `pending`이면 비활성·`aria-busy`. 중복 클릭을 줄이며 서버의 중복 검사까지 대신하지 않음 |
| `TextField` | 필수 ID로 라벨 연결, 힌트·오류를 `aria-describedby`에 연결, 오류 때 `aria-invalid`. 색상 외에도 오류를 전달 |
| `ConfirmDialog` | 브라우저 기본 `<dialog>` 재사용. 취소에 첫 초점, Tab 순환·Escape 취소·열었던 버튼으로 복귀 |
| `StatePanel` | loading·empty·error·forbidden·preparing 표현. 상태 설명과 다음 행동을 조합 |

미리보기의 삭제는 **현재 입력한 예시 내용 지우기**다. 게시글·DB 삭제를 수행하지 않는다. 실제 기능별 삭제 영향·권한 확인은 그 기능을 연결할 때 검증한다.

## 작은 예제: 입력 → 검증 → 로컬 처리 → 화면

`src/app/ui-preview/preview-client.tsx`의 흐름을 줄인 설명용 예다.

```tsx
const length = Array.from(title.trim()).length;
if (length < 1 || length > 100) {
  setTitleError("제목은 1~100자로 입력해 주세요.");
  titleRef.current?.focus();
  return;
}
setPending(true);
// 실제 예시는 1초 후 pending을 해제하고 완료 안내만 표시한다.
// API 호출·게시글 생성·서버 저장은 없다.
```

입력은 제목과 본문이다. 제목 앞뒤 공백을 제외한 Unicode 코드 포인트 수를 검사하고, 실패하면 제목에 오류·초점을 주며 본문은 유지한다. 성공하면 약 1초간 버튼을 비활성화하고 “서버에는 저장하지 않았습니다”를 표시한다. 이는 UI 확인이며 실제 작성 API의 서버 입력·인증·권한 검사가 아니다.

## 개발용 검토 화면

`/ui-preview`는 입력·확인창·상태 표현을 직접 확인하는 화면이다. 일반 메뉴에 링크를 넣지 않았고 `NODE_ENV === "development"`에서만 제공한다. 개발 서버에서는 200, 프로덕션 서버에서는 404를 실제 확인했다. 제목은 “공통 화면 검토”로 설정하고 robots `noindex, nofollow` 응답도 확인했다. 환경 분기가 접근 제어를 대신하지는 않는다.

모든 StatePanel 샘플은 화면 내부 예시다. 재시도 버튼은 로컬 상태만 바꾸며 실제 조회·네트워크 오류·접근 권한을 판정하지 않는다. 새로고침하면 입력이 사라진다.

## 실제 검사와 남은 한계

| 검사 | 실제 결과 |
| --- | --- |
| 타입·린트·빌드 | `pnpm typecheck`·최종 `pnpm lint` exit 0. 색상·검토 화면 제목 보완 후 최종 `pnpm build` exit 0, 타입 검사 포함 |
| 프로덕션 HTTP | `pnpm start`의 3001번 서버에서 `/` 307→`/posts`, 준비 화면 5개 200·한국어 안내, 잘못된 경로·`/ui-preview` 404 |
| health | GET 200·정확한 JSON, POST 405. DB 연결 검증과 별개 |
| 개발 HTTP | 프로덕션 종료 후 개발 서버 3001 재실행. `/posts`·`/ui-preview` 200, 검토 화면 robots 확인 |
| 탐색·키보드 | 친구→쪽지→채팅→로그인 메뉴와 현재 위치 일치. 첫 Tab의 본문 바로가기→Enter로 main 초점 이동 |
| 화면 너비 | 실제 CSS innerWidth 1280/clientWidth 1269, 814/803, 360/349에서 가로 넘침 없음. 모바일 메뉴 닫기·초점 복귀·이동 후 닫힘 확인 |
| 입력·확인창 | 빈 제목·101자 거부, 본문 유지·초점·오류 연결, 처리 중 버튼, 상태 재시도, 취소·확인·키보드 순환·복귀 확인 |

모바일 CSS 너비 360에서는 검토 화면이 한 열(315px)이었고 확인창 좌우 18~331px이 본문 화면 349px 안에 들어왔다. 공통 버튼 높이는 44px로 확인했다. 실제 휴대 기기·모든 브라우저·실제 오류 경계 장애·업무 API·DB·Auth·Realtime은 미검증이다. 데스크톱·확인창 캡처는 검토 자료에 있고 모바일 캡처는 첨부하지 않았다.

## 면접 질문·확인 상태

1. **버튼 비활성화만으로 중복 저장을 막을 수 있나요?** 현재는 연속 클릭을 줄이는 UI다. 직접 요청·재시도·동시 요청은 이후 서버 계약과 DB 제약으로 별도 처리해야 한다.
2. **확인창에서 취소와 초점 복귀가 필요한 이유는 무엇인가요?** 키보드 사용자가 의도치 않게 지우지 않고 원래 작업으로 돌아가도록 한다. 실제 삭제 대상·권한은 기능 연결 때 별도로 검증한다.

설명과 검증 근거는 제공했으며 사용자 이해·복습 완료는 확인하지 않았다. 현재·다음 ID는 `02-UI-REVIEW / WAITING_USER_REVIEW`다. 수정 요청은 같은 REVIEW에서 수정·재검증한다. 사용자 확인 후 `02-UI-COMMIT`, 성공 후 `03-SETUP-01`로 이어간다.
