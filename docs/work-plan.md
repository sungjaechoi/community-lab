# community-lab 풀스택 포트폴리오 실행 플랜

프론트엔드 경험을 바탕으로 Next.js에서 화면, 서버 API, PostgreSQL, 인증·인가, 실시간 통신을 연결하는 학습형 프로젝트다. 각 기능을 API와 UI로 나누어 만들고, 사용자가 동작을 확인한 뒤 각각 커밋한다. 결과와 함께 선택한 이유, 실패 처리, 실제 검증 근거를 GitHub 포트폴리오에 남긴다.

**개정 2 · 2026년 10월 26일.** 기존 16개 STEP을 유지하면서 환경 설정의 담당자·인계 조건, 공통 UI, 기능별 API/UI 작업, 사용자 확인과 커밋을 세분화했다. 14주와 주 8~12시간은 원래의 일정 추정치다. 확인·수정에 드는 시간을 포함한 새 일정은 실제 진행 속도로 조정한다.

## 시작 위치와 문서 역할

| 파일 | 역할 | 앱 저장소를 만든 뒤의 정식 위치 |
| --- | --- | --- |
| AGENTS.md | 읽기 순서, 설명 방식, 확인 대기와 커밋 규칙 | 앱 루트의 AGENTS.md |
| community-lab-work-plan.md | 목표·WHY·작업 순서·완료 기준 | docs/work-plan.md |
| docs/work-status.md | 현재 작업, 확인 대기, 검증 결과, 커밋, 다음 ID | docs/work-status.md |
| START-HERE.md | 처음 시작·기존 프로젝트에 병합·재개하는 방법 | 필요할 때 참고 |

이 파일은 실행 계획이며 현재 구현 상태를 증명하지 않는다. **현재 상태는 진행 기록과 실제 코드·검증 결과로 확인한다.** 새 작업이라면 `01-01`부터 시작한다. 이미 진행 중이라면 기존 완료 이력을 보존하고 추가된 항목만 확인한다. 파일을 저장하는 것만으로 작업이 실행되지는 않는다.

### 처음 시작할 때

```text
현재 작업 폴더의 AGENTS.md를 읽고 적용해줘.
docs/work-status.md와 실제 파일을 확인한 뒤 이 플랜의 STEP 01을 진행해줘.
각 작업의 목적과 WHY를 쉽게 설명하고 필요한 경우 짧은 예제로 보여줘.
요구사항·화면 목록·정책·수용 기준을 정리한 뒤 01-REVIEW에서 내가 확인할 수 있게 멈춰줘.
완료한 작업, 확인 대기 항목, 다음 작업 ID를 기록해줘.
이미 진행한 기록이 있으면 보존해서 이어가줘.
```

### 이어서 진행할 때

```text
AGENTS.md와 docs/work-status.md, 실제 변경 내용을 읽어줘.
진행 기록의 정식 플랜에서 현재 또는 다음 미완료 STEP 하나를 진행해줘.
요청 범위 안의 구현과 검증은 계속하되, 정해진 사용자 확인 지점에서는 자료를 제시하고 멈춰줘.
이미 내가 확인한 범위는 해당 커밋을 실행한 뒤 다음 작업으로 이어가줘.
WHY, 실제 검증 결과, 사용자 확인 상태, 커밋, 다음 작업 ID를 기록해줘.
```

## 기능을 만드는 기본 순서

**API 구현·검증 → API 사용자 확인 → API 커밋 → UI 구성·API 연결·검증 → UI 사용자 확인 → UI 커밋**을 적용한다. API 확인은 완성된 화면 없이도 요청·응답과 데이터 변경을 재현할 수 있게 준비한다.

| 단계 | 코덱스가 준비할 결과 | 다음 단계에 들어가는 조건 |
| --- | --- | --- |
| API 구현·검증 | 계약, 서버·DB 코드, 입력·권한·실패 검증, 사용자용 재현 방법 | 실제 검증 결과와 확인 자료가 준비됨 |
| API 사용자 확인 | 요청 방법, 기대 응답, 실제 결과, DB 영향, 변경 파일 | 사용자가 현재 API 범위를 확인함 |
| API 커밋 | 확인된 파일만 커밋하고 실제 해시 기록 | 커밋 성공 |
| UI 구성·연결·검증 | 화면별 구현, 실제 API 연결, 로딩·빈 상태·실패·권한 처리 | 실제 화면과 확인 절차가 준비됨 |
| UI 사용자 확인 | 접속 주소, 사용자 역할, 클릭 순서, 기대 결과, 검증 결과 | 사용자가 현재 UI 범위를 확인함 |
| UI 커밋 | 확인된 UI 범위를 커밋하고 다음 작업 기록 | 커밋 성공 |

`REVIEW`는 실제로 멈추는 지점이다. 자동 테스트 성공, 화면 캡처 생성, 침묵, 시간 경과를 사용자 확인으로 바꾸지 않는다. 수정 요청이 있으면 같은 묶음에서 수정·검증하고 다시 확인을 요청한다. 확인 후 동작 범위를 추가로 바꿨다면 달라진 부분을 다시 제시한다.

사용자가 “07 API 확인 완료. 커밋하고 UI 진행해줘”라고 하면 같은 범위의 커밋 허락을 다시 묻지 않는다. 커밋이 실패하면 이유를 해결하거나 기록하고, 완료한 것처럼 다음 묶음으로 넘어가지 않는다. 범위가 모호한 응답은 현재 대기 중인 확인 항목과 연결할 수 있는지 먼저 살핀다.

기본 실행 범위는 현재 또는 다음 미완료 STEP 하나다. 전체 구현을 요청하더라도 이 플랜의 사용자 확인 지점은 유지한다. 학습용 면접 질문은 답을 기다려야 하는 승인 절차가 아니다. 환경·ERD·문서 단계는 결과 확인과 커밋을 적용하고 불필요하게 API/UI를 만들지 않는다.

## 외부 계정·환경 작업을 넘기는 방법

Git이나 Supabase 작업의 담당자는 **실제 도구·인증 상태·권한**을 확인한 뒤 정한다. 계정 화면이 필요하다는 이유만으로 모든 작업을 사용자에게 넘기거나, 접근 권한이 없는 상태에서 설정이 끝났다고 기록하지 않는다.

| 구분 | 코덱스가 진행할 수 있는 작업 | 사용자의 참여가 필요한 경우 |
| --- | --- | --- |
| 로컬 환경 | 폴더·버전 조사, Next.js 생성, 코드·설정·검증 | 설치 권한, 사용자 기기에서 직접 실행해야 할 때 |
| Git·GitHub | 저장소·브랜치·remote 조사, 허용된 저장소 준비, 연결 검증, 커밋, 정해진 정책의 push | 계정·조직·공개 범위 선택, 로그인·MFA·조직 권한 승인 |
| Supabase | 접근 가능한 도구로 프로젝트 확인, 설정 파일, SQL, 연결 검사, migration | 계정 로그인, 프로젝트 선택·생성 권한, 보안 입력란에 비밀값 입력 |
| Google OAuth | callback·redirect 값 정리, 서버 코드, 로그인 검증 | Google Cloud 계정·동의 화면·OAuth 자격 증명 설정에 접근이 필요할 때 |
| Vercel·CI | 빌드·배포 설정, workflow, 실제 결과 확인 | 저장소 연결 허용, secrets 등록, 프로젝트·배포 환경 선택에 접근이 필요할 때 |

인계 시에는 **작업 ID / 필요한 이유 / 정확한 주소와 화면 항목 / 입력할 값의 종류 / 완료 후 알려 줄 비밀이 아닌 정보 / 재개할 검증 ID**를 제공한다. 비밀번호·토큰을 채팅에 붙여 넣게 하지 않는다. 사용자가 “입력 완료”라고 알려 주면 실제 연결을 검증한 뒤 해당 항목을 완료한다. 접근이 막혀도 같은 묶음에서 가능한 준비를 끝내고 차단 사유를 기록한다.

## Git 운영 규칙

1. STEP 02에서 기존 저장소·원격 이력·계정·브랜치를 조사한다. 새 프로젝트에서만 초기화하고 기존 앱과 원격 이력을 보존한다.
2. 저장소 이름·소유 계정·공개 범위·작업 브랜치·push 정책을 기록한다. 이미 정해진 선호와 권한은 다시 묻지 않는다. 미정인 push 정책의 기본값은 로컬 커밋까지다.
3. 사용자 확인 후 그 범위만 커밋한다. 먼저 기존 staged 변경을 확인하고, 관련 파일만 지정한다. `git add .`나 `git commit -a`로 무관한 변경까지 포함하지 않는다. 다른 작업의 staged 내용은 임의로 해제하지 않는다.
4. 커밋 메시지는 목적을 드러내게 쓴다. 예: `feat(posts): add validated CRUD API`, `feat(posts): connect list and editor UI`. 실제 커밋 해시와 포함 범위를 기록한다.
5. **commit은 로컬 이력, push는 원격 브랜치 반영**이다. 허용된 push 정책을 따르고, 이미 허용되었다면 매번 다시 묻지 않는다. push가 배포를 유발하는 브랜치인지도 확인한다. 서명·훅·브랜치 보호를 끄거나 강제 push로 문제를 우회하지 않는다.
6. 커밋 해시는 커밋 성공 후 진행 기록에 넣는다. 그 기록 변경은 다음 예정 커밋에 포함한다. 자기 자신의 해시를 넣기 위해 기록용 커밋을 반복하지 않는다.

Git의 로컬 이력과 원격 반영 절차는 [GitHub 공식 안내](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github)를 참고한다.

## 상태와 완료 기준

| 상태 | 뜻 |
| --- | --- |
| 미확인 | 기존 진행·환경을 아직 조사하지 않음 |
| TODO · 미시작 | 조사 결과 아직 시작하지 않음 |
| IN_PROGRESS · 진행 중 | 설계·구현·수정 중 |
| VERIFYING · 검증 중 | 실제 동작과 완료 조건을 확인 중 |
| WAITING_USER_ACTION · 사용자 작업 대기 | 계정·설정 인계가 필요하며 재개 조건을 기록함 |
| WAITING_USER_REVIEW · 사용자 확인 대기 | 확인 자료를 제출했으며 현재 REVIEW에서 멈춤 |
| APPROVED · 확인 완료·커밋 대기 | 사용자가 해당 범위를 확인했고 COMMIT이 다음 작업 |
| DONE · 완료 | 해당 작업의 증거가 있음. 묶음 완료는 필요한 확인·커밋까지 성공 |
| BLOCKED · 차단 | 환경·선행 작업·검증 실패 등의 원인이 해결되지 않음 |
| DEFERRED · 선택 보류 | 필수 프로젝트 완료를 막지 않는 선택 기능 |

구현, 사용자 확인, 학습 상태를 따로 적는다. 설명을 제공했다고 사용자의 이해까지 완료로 단정하지 않는다. 실제로 실행하지 못한 테스트·연결·성능 측정은 미검증으로 남긴다. 예상 결과를 실제 결과로 기록하지 않는다.

진행 기록에는 현재 STEP·묶음·작업 ID·상태, 변경 파일, 검증 결과, 사용자 확인 범위와 실제 응답, 커밋 해시, 외부 작업 인계, 다음 ID를 남긴다. 확인 대기 중 현재 ID와 다음 재개 ID는 해당 `REVIEW`이며, 확인을 받으면 `COMMIT`, 커밋 성공 후에 다음 구현 ID로 바뀐다. STEP 01은 예외로 확인 후 `01-RECORD`를 수행하고, 문서 커밋은 `02-ENV-COMMIT`에 포함한다. 앞선 사용자의 확인을 새 변경 범위에 자동 적용하지 않는다.

## 기존 플랜을 사용 중인 경우

이번 개정은 작업을 더 작게 나눈 것이다. 기존 진행 기록을 새 템플릿으로 덮어쓰거나 미시작으로 초기화하지 않는다. 같은 숫자라도 의미가 달라질 수 있으므로 코드·검증·사용자 확인·Git 이력을 보고 대응시킨다.

| 기존 항목 | 개정 2에서 확인할 곳 | 이관할 때 주의할 점 |
| --- | --- | --- |
| STEP 01 01-01~06 | STEP 01 같은 ID, 01-07~08·REVIEW 추가 | 기존 정책을 유지하고 화면·확인 기준을 보완 |
| STEP 02 02-01~07 | 02-ENV / 02-GIT / 02-UI | Git 연결과 UI 기초를 완료로 추정하지 않음 |
| STEP 03 03-01~07 | 03-SETUP / 03-REVIEW / 03-COMMIT | 입력 완료와 실제 앱 DB 연결을 구분 |
| STEP 06~09 | 각 STEP의 API / UI | API가 있어도 화면 검증·확인은 별개 |
| STEP 10 | FRIEND API·UI, INBOX API·UI | 친구와 쪽지의 완료를 각각 확인 |
| STEP 11~13 | 각 STEP의 API / UI | 실시간 복원·페이지네이션의 화면 동작 포함 |
| STEP 04·05·14~16 | 같은 큰 STEP의 세분화된 ID | 기존 설계·SQL·CI·배포 결과를 보존 |

`docs/work-status.md`에 기존 ID, 새 ID, 보존한 증거, 추가로 필요한 작업을 적는다. 과거 사용자 확인이 없는데 있었던 것으로 만들지 않는다. 이미 커밋된 기능은 확인을 위해 이력을 다시 쓰지 않고, 현 상태의 검수와 필요한 보완을 기록한다.

## STEP 03 Supabase 프로젝트·환경 변수·DB 연결

**목표와 WHY:** Supabase 프로젝트를 준비하고 Next.js가 실제 PostgreSQL에 연결되는지 확인한다. 대시보드 접속, 연결 정보 입력, 앱의 연결 성공은 서로 다른 결과다. DB 엔진과 관리 화면·클라이언트의 역할도 구분한다.

**선행 조건:** STEP 02 완료. **진행 상태:** `docs/work-status.md`에서 확인.

### 실행 순서

- [ ] **03-SETUP-01** 기존 Supabase 계정·조직·프로젝트·접근 도구와 권한을 확인한다. 개발용 프로젝트인지 식별하고 기존 프로젝트를 임의로 바꾸지 않는다.
- [ ] **03-SETUP-02** 개발 프로젝트를 준비한다. 도구로 가능한 범위는 진행하고 로그인·프로젝트 선택·생성 권한·비밀 입력이 필요한 부분은 아래 인계표로 안내한다. 프로젝트 이름·용도·지역 등 비밀이 아닌 정보만 기록한다.
- [ ] **03-SETUP-03** 프로젝트의 Connect 및 API 키 화면에서 실제 Project URL과 publishable key의 위치를 확인한다. 브라우저 클라이언트용 값과 PostgreSQL 접속 자격 증명을 구분한다. 필요하지 않은 서버 비밀키를 추가하지 않는다.
- [ ] **03-SETUP-04** 런타임·migration·관리 도구의 연결 방식을 고른다. 서버리스 런타임은 transaction pooler, migration은 direct 연결을 우선 검토한다. 네트워크·도구 제약으로 session pooler가 필요하면 호환성을 확인한다. 실제 호스트·포트·사용자명은 Connect 화면에서 가져온다.
- [ ] **03-SETUP-05** 실제 비밀값은 로컬 환경 파일이나 제공된 보안 입력란에 넣는다. `.env.example`에는 변수 이름·용도·자리표시자만 둔다. Git 추적과 ignore 상태를 확인하고 환경 파일 전문이나 URL 자격 증명을 출력하지 않는다.
- [ ] **03-SETUP-06** 서버 전용 연결 검증 코드와 필요한 PostgreSQL 드라이버·환경 변수 로더를 준비한다. Next.js 밖에서 실행하는 스크립트도 올바른 환경 파일을 명시적으로 읽고, 값이 빠졌으면 분명히 실패하도록 한다.
- [ ] **03-SETUP-07** 개발 환경에서 런타임 URL과 migration URL을 각각 읽기 쿼리로 확인한다. 연결 대상·역할·TLS 설정을 검사하고 비밀을 제거한 결과만 남긴다. DB 정보를 공개 health 응답에 넣지 않는다.
- [ ] **03-SETUP-08** SQL Editor와 DBeaver에서 같은 개발 DB를 확인한다. 관리 도구의 연결 성공을 앱의 연결 성공으로 대신하지 않는다. 사용자의 기기에서만 가능한 DBeaver 작업은 실제 연결 절차와 확인 쿼리를 인계한다.
- [ ] **03-SETUP-09** 테스트 DB·Auth 기반을 개발·운영과 분리해 준비한다. 로컬 Supabase 또는 별도 테스트 프로젝트 등 가능한 방식을 정한다. 준비가 막혔다면 담당자·재개 ID를 기록하며, 통합 테스트를 실행하는 STEP 05 이전에 해결한다.
- [ ] **03-SETUP-10** Data API의 노출 스키마·기본 권한을 조사하고, 새 테이블 생성과 함께 적용할 GRANT·REVOKE·RLS 원칙을 적는다. 앱의 DB 역할과 migration 역할을 STEP 05에서 분리·검증할 계획을 남긴다.
- [ ] **03-SETUP-11** 환경 변수별 공개 여부·사용 위치·관리 방법, 각 연결의 실제 성공·실패, 사용자에게 필요한 미완료 작업을 문서화한다. 인증·DNS·네트워크·잘못된 연결 방식 등의 원인을 구분한다.
- [ ] **03-REVIEW** 사용자가 개발 프로젝트, 환경별 연결 용도, 앱·관리 도구의 실제 연결 결과를 확인하도록 제시하고 **멈춘다**. 비밀값 입력 완료만으로 연결 검증을 완료하지 않는다.
- [ ] **03-COMMIT** 확인된 연결 코드·설정 예시·문서를 커밋한다. 비밀값 파일은 제외하고 실제 해시, 남은 외부 작업, `04-01`을 기록한다.

화면 메뉴 이름은 실행 시점의 공식 문서·실제 화면을 확인한다. `.env.local`을 채팅으로 보내 달라고 요청하지 않는다.

```dotenv
# .env.example: 실제 비밀값은 넣지 않는다
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
DATABASE_URL=
MIGRATION_DATABASE_URL=
NEXT_PUBLIC_SITE_URL=http://localhost:3000
```

`NEXT_PUBLIC_` 값은 브라우저에 노출될 수 있다. DB URL·비밀번호·서버 비밀키는 여기에 넣지 않는다. publishable key는 사용자 인가를 대신하지 않는다. 테스트 실행은 별도 환경의 URL을 주입하며 개발·운영 DB로 자동 대체하지 않는다.

```sql
SELECT 1 AS connection_ok, current_database(), current_user;
```

이 쿼리는 데이터를 변경하지 않고 연결과 실행 역할을 확인한다. 결과와 연결 문자열은 다르다. 기록에는 필요한 대상·역할 정보만 남긴다. transaction pooler를 사용할 때는 드라이버의 prepared statement·연결 수·TLS 설정도 확인한다. [Supabase 연결 방식](https://supabase.com/docs/guides/database/connecting-to-postgres), [Drizzle과 Supabase](https://orm.drizzle.team/docs/connect-supabase).

**산출물:** `docs/development-setup.md`, 환경 변수 명세, 서버 전용 연결 점검 코드, 분리된 테스트 환경 준비 기록, 사용자 확인과 커밋.

**완료 기준:** 설정 입력과 앱의 실제 연결 성공을 구분해 기록했고, 개발·테스트·운영 대상이 혼동되지 않는다. 필수 연결이 실패한 경우 다음 DB 작업을 완료로 진행하지 않는다.

**기본 개념:** PostgreSQL, DB 클라이언트, connection string, connection pool, SSL/TLS, 환경 분리.

**면접 질문:** “서버리스에서 연결 풀을 고려하는 이유는 무엇인가요?” 실행 인스턴스 수, 인스턴스별 연결 수, 재사용 관점으로 설명한다.

**워크 요청:** `STEP 03을 진행해줘. 계정에서 내가 해야 할 일과 코드 작업을 나누고, 실제 DB 연결을 검증한 뒤 03-REVIEW에서 확인을 기다려줘.`

## STEP 04 ERD와 데이터 제약조건 설계

**목표와 WHY:** 화면·API가 공유하는 데이터 관계를 설계하고 잘못된 데이터가 저장되지 않도록 DB의 책임을 정한다. 화면에 필요한 데이터가 모델에서 어떻게 나오는지도 함께 확인한다.

**선행 조건:** STEP 03의 필수 연결 확인·커밋. **진행 상태:** `docs/work-status.md`에서 확인.

### 실행 순서

- [ ] **04-01** `profiles`, `posts`, `comments`, `friend_requests`, `friendships`, `inbox_messages`, `conversations`, `messages`의 역할을 적는다. 참여자 별도 테이블의 필요성도 비교한다.
- [ ] **04-02** `profiles.id`와 Supabase `auth.users.id`, 작성자·수신자·채팅 참여자의 관계를 ERD로 표시한다. Auth가 관리하는 스키마를 앱 migration으로 재생성하지 않는다.
- [ ] **04-03** 테이블별 PK·FK·NOT NULL·UNIQUE·CHECK와 삭제 정책을 정한다. 사용자·게시글·부모 댓글 삭제에 따른 자식 데이터의 처리를 설명한다.
- [ ] **04-04** 친구 쌍과 1대1 채팅 쌍을 일관된 UUID 순서로 정규화한다. 자기 관계·역방향 중복을 막는 제약을 정의하고 앱·DB의 비교 규칙을 일치시킨다.
- [ ] **04-05** 댓글 `parent_id`가 같은 게시글을 가리키며 깊이 1단계를 넘지 않도록 보장할 위치를 정한다. FK만으로 모든 비즈니스 규칙이 보장된다고 가정하지 않는다.
- [ ] **04-06** 채팅 재전송의 중복 저장을 막을 `client_message_id`와 유일성 범위를 설계한다. 예: `(conversation_id, sender_id, client_message_id)` UNIQUE. 화면 중복 이벤트 제거와 구분한다.
- [ ] **04-07** 수신함, 게시글별 댓글, 친구 수락, 채팅 기록 조회를 ERD에 대입한다. 각 화면에서 필요한 컬럼·정렬·조회 범위를 적고 과한 응답 노출을 줄인다.
- [ ] **04-08** 동시 요청과 삭제 시나리오를 작은 예로 설명한다. 서버 검증, DB 제약, 트랜잭션이 각각 책임지는 조건을 정리하고 미정 정책을 확인 자료에 넣는다.
- [ ] **04-REVIEW** ERD·제약·삭제 정책·화면 데이터 연결을 사용자가 확인하도록 제시하고 **멈춘다**.
- [ ] **04-COMMIT** 확인된 설계 문서를 커밋하고 실제 해시와 `05-01`을 기록한다.

**산출물:** `docs/erd.md`, `docs/decisions/0002-database-design.md`, API·화면별 데이터 표, 확인 기록과 커밋.

**완료 기준:** 각 FK·UNIQUE가 막는 실패와 삭제 결과를 설명할 수 있다. UUID 문자열의 표기 차이에 기대지 않고 실제 DB 제약과 맞는 정규화 방식을 선택했다.

**기본 개념:** PK, FK, 1:N, N:M, 정규화, 참조 무결성, CHECK, UNIQUE.

**면접 질문:** “서버에서 중복 확인을 해도 UNIQUE가 필요한 이유는 무엇인가요?” 두 요청이 동시에 사전 검사에 통과하는 예로 설명한다. [PostgreSQL 제약조건](https://www.postgresql.org/docs/current/ddl-constraints.html).

**워크 요청:** `STEP 04를 진행해줘. 화면·API에 필요한 관계와 제약조건을 설계하고 04-REVIEW에서 예시와 함께 확인받아줘.`

## STEP 05 Drizzle과 migration 구성

**목표와 WHY:** DB 변경을 코드와 SQL 이력으로 재현한다. ORM이 만든 SQL을 읽고 실제 DB 역할·권한·제약조건이 의도대로 작동하는지 확인한다.

### 실행 순서

- [ ] **05-01** 호환되는 Drizzle ORM·Kit·PostgreSQL 드라이버·환경 로더를 준비한다. 기존 설치를 재사용하고 안정 버전과 prerelease를 무심코 섞지 않는다. 실제 버전을 기록한다.
- [ ] **05-02** `src/db/schema/`, 서버 전용 `src/db/index.ts`, `drizzle.config.ts`를 구성한다. 런타임 `DATABASE_URL`과 도구용 `MIGRATION_DATABASE_URL`을 분리하고 Drizzle CLI에도 환경 변수를 명시적으로 로딩한다.
- [ ] **05-03** 우선 `profiles`, `posts` 스키마를 정의한다. 나머지 테이블은 해당 기능에서 추가한다. FK·기본값·제약·삭제 정책을 ERD와 대조한다.
- [ ] **05-04** migration SQL을 생성하고 읽는다. 아직 적용하지 않고 새 테이블의 GRANT·REVOKE·RLS 등 초기 접근 제한 SQL도 준비한다.
- [ ] **05-05** 테이블 생성과 필요한 초기 접근 제한이 같은 트랜잭션에서 적용되는지 확인한다. migration 실행기의 실제 동작을 조사하고 노출 공백이 없는 적용 단위를 만든다. 정책·트리거 변경도 SQL 이력으로 관리한다.
- [ ] **05-06** 런타임 역할과 migration 역할의 권한을 구분한다. 런타임은 필요한 DML 중심으로 구성하고 소유권·BYPASSRLS·GRANT와 실제 RLS 동작을 조사한다. 사용자 JWT 문맥이 자동 주입된다고 가정하지 않는다.
- [ ] **05-07** 정확한 개발 DB를 확인한 뒤 준비한 migration을 적용한다. 적용 전후 상태와 migration 이력을 기록하고 대시보드에서 한 임시 변경도 코드·SQL로 회수한다.
- [ ] **05-08** 필요한 Supabase Auth 기반을 갖춘 분리 테스트 환경에서 같은 migration을 처음부터 적용한다. 재실행 시 이미 적용한 변경을 중복 실행하지 않는지도 확인한다. 운영 DB에 테스트를 실행하지 않는다.
- [ ] **05-09** 지원되는 Auth 관리 방법으로 개발·테스트 사용자를 준비한 뒤 연결된 프로필의 INSERT·SELECT를 확인한다. `auth.users` FK가 있는데 임의 UUID만 넣어 검증하지 않는다. 권한 거부와 제약 위반도 확인한다.
- [ ] **05-10** 생성 SQL, 역할별 접근, 재현 절차, 실패 원인·복구 방법을 정리한다. DB 오류 전문이나 비밀값을 공개 응답에 넣지 않는다.
- [ ] **05-REVIEW** SQL이 바꾸는 내용과 실제 적용·재현 결과를 설명하고 사용자의 확인을 **기다린다**. 미검증·권한 예외를 숨기지 않는다.
- [ ] **05-COMMIT** 확인된 스키마·SQL·설정·검증·문서를 커밋하고 실제 해시와 `06-AUTH-01`을 기록한다.

```ts
// drizzle.config.ts: 개발 환경을 읽는 부분의 예시
import { config } from "dotenv";
config({ path: ".env.local" });

if (!process.env.MIGRATION_DATABASE_URL) {
  throw new Error("MIGRATION_DATABASE_URL is required");
}
```

이후 `defineConfig`에 스키마 위치·출력 경로·실제 DB URL을 연결한다. 테스트·CI에서는 해당 환경의 URL을 명시적으로 주입하고 잘못된 환경으로 대체되지 않게 한다. Next.js 런타임 밖에서의 환경 로딩은 [공식 안내](https://nextjs.org/docs/app/guides/environment-variables)를 참고한다.

```bash
# 설치·설정이 준비된 뒤 변경 SQL을 생성
pnpm exec drizzle-kit generate
pnpm exec drizzle-kit generate --custom --name=access-policies
# 생성·정책 SQL과 적용 트랜잭션을 검토한 다음 실행
pnpm exec drizzle-kit migrate
```

`generate`는 변경을 작성하고 `migrate`는 적용한다. custom migration은 정책·트리거처럼 직접 쓴 SQL을 이력에 남긴다. 위 명령이 분리되어 있다는 이유만으로 적용 단위까지 안전하다고 가정하지 않는다. [Drizzle custom migrations](https://orm.drizzle.team/docs/kit-custom-migrations).

**산출물:** 스키마·DB 접근 코드, `drizzle/`, `docs/database-migrations.md`, 역할·경로별 권한 표, 실제 재현 근거와 커밋.

**완료 기준:** 앱 스키마와 접근 정책을 재현했다. Drizzle 직접 연결은 사용자 JWT를 자동 전달하지 않으며 `auth.uid()` 기반 RLS가 그대로 작동하지 않을 수 있음을 실제 역할 조사로 설명했다.

**기본 개념:** ORM, SQL, migration, schema drift, DDL·DML, DB 역할.

**면접 질문:** “ORM을 쓰는데 SQL과 migration을 알아야 하는 이유는 무엇인가요?” 성능·무결성·권한·변경 이력의 재현성으로 설명한다.

**워크 요청:** `STEP 05를 진행해줘. SQL과 접근 정책을 함께 준비해 개발·테스트 환경에서 검증하고 05-REVIEW에서 확인 자료를 제시해줘.`

## STEP 06 Google 로그인·세션 API와 로그인 UI

**목표와 WHY:** 요청한 사용자가 누구인지 서버에서 검증하고 로그인 상태를 화면에 일관되게 보여 준다. Google·Supabase·앱의 리디렉션, 쿠키 세션, 서버 인증과 UI 표시를 구분해 이해한다.

**선행 조건:** STEP 05 완료, STEP 02 공통 UI. **진행 상태:** `docs/work-status.md`에서 확인.

### A. 외부 OAuth 설정 준비

- [ ] **06-AUTH-01** Supabase Auth와 [Google Cloud Console](https://console.cloud.google.com/)에 필요한 접근이 있는지 확인한다. 사용자 계정·프로젝트·테스트 범위를 정하고 로그인·권한 승인이 필요한 작업만 인계한다.
- [ ] **06-AUTH-02** Google OAuth 동의 화면·클라이언트·테스트 사용자를 준비한다. Google에 등록하는 Supabase callback URL은 실제 대시보드 값을 사용한다. 자격 증명은 해당 서비스의 보안 입력란에 보관한다.
- [ ] **06-AUTH-03** Supabase Google Provider와 앱의 Site URL·허용 redirect URL을 설정한다. Google → Supabase의 callback과 Supabase → 앱의 callback을 구분해 표로 남긴다. 개발 URL부터 맞춘다.
- [ ] **06-AUTH-04** 설정 완료 여부·남은 계정 작업·검증할 A/B 사용자를 기록한다. 계정 화면 접근이 없으면 필요한 항목과 정확한 재개 ID를 안내한다. 코드 준비는 가능한 범위까지 진행한다.

계정 설정은 [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-sign-in/auth-google)을 기준으로 실제 화면을 확인한다. 앱 저장소에 Google client secret을 복사할 필요가 있는지부터 판단하고, 불필요한 비밀값을 추가하지 않는다.

### B. 인증·세션 API 구현과 확인

- [ ] **06-API-01** 로그인 시작·callback·로그아웃·현재 사용자 조회의 계약과 실패 처리를 정한다. 예: `/auth/sign-in`, `/auth/callback`, `POST /api/auth/sign-out`, `GET /api/me`. 실제 채택 경로를 문서화한다.
- [ ] **06-API-02** Supabase JS·SSR 클라이언트를 설치 버전에 맞춰 구성하고 브라우저용·서버용 책임을 나눈다. 서버 전용 값과 쿠키 처리 코드가 클라이언트 번들에 섞이지 않도록 한다.
- [ ] **06-API-03** 브라우저에서 직접 열 수 있는 로그인 시작 경로, callback의 세션 교환, 실패 응답을 구현한다. 로그인 후 이동 경로는 검증한 앱 내부 경로로 제한한다. 아직 로그인 화면 버튼은 만들지 않는다.
- [ ] **06-API-04** 설치한 Next.js 버전에 맞는 `proxy.ts` 또는 `middleware.ts`와 세션 갱신을 연결한다. 공식 SSR 예제를 그대로 복사하기 전에 현재 버전의 쿠키·캐시 동작을 확인한다.
- [ ] **06-API-05** 검증된 사용자 ID를 반환하는 공통 서버 인증 함수를 만든다. `GET /api/me`와 보호된 예제 요청으로 검증한다. 클라이언트의 `userId`나 검증하지 않은 세션 객체를 인증 근거로 쓰지 않는다.
- [ ] **06-API-06** 로그아웃·만료·갱신 실패를 처리하고 쿠키 기반 변경 요청의 방어와 개인 응답 캐시 정책을 검토한다. A의 데이터·세션 응답이 B에게 공유되지 않게 한다.
- [ ] **06-API-07** 첫 로그인 프로필 생성·기존 프로필 재사용·중복 요청 처리를 구현한다. 생성 실패·재시도 정책을 정하고 DB 제약과 함께 검증한다.
- [ ] **06-API-08** A·B 사용자로 로그인 시작 경로, callback, 현재 사용자 조회, 로그아웃·새로고침·만료·보호 API 거부를 확인한다. 실제 Google 로그인과 자동 테스트의 검증 범위를 구분한다.
- [ ] **06-API-09** 완성된 로그인 UI 없이도 확인할 절차를 작성한다. 사용자가 로그인 시작 URL을 열고 Google 인증 후 현재 사용자 API를 확인하게 한다. 토큰·쿠키를 채팅이나 문서로 복사하게 하지 않는다.
- [ ] **06-API-REVIEW** OAuth 흐름, 요청·응답, A/B 격리, 실패 처리와 변경 범위를 제시하고 사용자의 API 확인을 **기다린다**.
- [ ] **06-API-COMMIT** 확인된 인증 서버·클라이언트 기반·검증·문서를 커밋하고 실제 해시를 기록한다. 성공 후 `06-UI-01`로 이동한다.

공식 SSR 구성은 [서버 인증 클라이언트](https://supabase.com/docs/guides/auth/server-side/creating-a-client)를 참고한다. 로그인 화면이 아직 없어도 시작 경로와 API 요청으로 서버 동작을 확인할 수 있다.

### C. 로그인 화면·사용자 메뉴 연결

- [ ] **06-UI-01** 로그인 화면의 설명·Google 버튼·로그인 후 이동 흐름을 구성한다. STEP 02의 공통 버튼과 레이아웃을 사용한다.
- [ ] **06-UI-02** 승인된 로그인 시작 경로와 연결한다. 진행 중, 사용자가 취소한 경우, Provider 오류, 재시도 화면을 구분한다.
- [ ] **06-UI-03** 현재 사용자 조회를 헤더 메뉴에 연결하고 로그인 상태·로그아웃 동작·로그인 필요 안내를 구현한다. 서버 인가를 UI 표시만으로 대체하지 않는다.
- [ ] **06-UI-04** 새로고침·탭 이동·로그아웃 후 화면 상태를 정리한다. 로그인 전에 있던 안전한 내부 화면으로 돌아갈 수 있는지, 오류 시 다음 행동이 분명한지 확인한다.
- [ ] **06-UI-05** 실제 로그인 흐름, 작은 화면·키보드 초점, 버튼 중복 실행·로딩 상태를 점검한다. 자동 검증과 실제 계정으로 확인한 범위를 나눠 기록한다.
- [ ] **06-UI-REVIEW** 실제 화면 주소와 로그인→새로고침→로그아웃·취소/실패 확인 순서를 제공하고 **멈춘다**.
- [ ] **06-UI-COMMIT** 확인된 로그인 UI·연결·검증·문서를 커밋하고 실제 해시와 `07-API-01`을 기록한다.

**산출물:** 인증·세션 API, 로그인 화면·사용자 메뉴, `docs/authentication.md`, API·UI 확인 절차와 별도 커밋.

**완료 기준:** API와 UI를 각각 확인·커밋했고 서버가 검증한 사용자 신원으로만 보호 작업을 수행한다. 로그인 성공·취소·실패·로그아웃·새로고침이 화면과 서버에서 일치한다.

**기본 개념:** OAuth 2.0, 인증·인가, JWT, access·refresh token, 쿠키, CSRF, 세션 갱신.

**면접 질문:** “프론트에서 로그인 여부를 확인해도 서버 검증이 필요한 이유는 무엇인가요?” UI를 거치지 않는 요청과 위조 입력으로 설명한다.

**워크 요청:** `STEP 06의 OAuth 설정과 인증 API를 진행해줘. 화면 없이 확인할 방법을 준비하고 06-API-REVIEW에서 멈춰줘.`

## STEP 07 게시글 API 구현 후 화면 연결

**목표와 WHY:** HTTP 요청을 서버 검증과 DB 변경으로 연결한다. 먼저 API의 입력·권한·응답을 확인하면, 이후 화면 문제와 서버 문제를 구분하기 쉽다. 작성자 인가는 첫 구현부터 포함한다.

**선행 조건:** STEP 06 완료. STEP 02에서 공통 레이아웃·내비게이션·반응형·폼·상태 표시 기반의 사용자 검수와 커밋이 완료되어 있어야 한다.

**진행 상태:** docs/work-status.md에서 확인.

### API 구현과 검증

- [ ] **07-API-01** 목록·상세·생성·수정·삭제의 API 계약을 `docs/api/posts.md`에 작성한다. 요청·응답·오류 코드, 제목과 본문의 최대 길이, 기본 페이지 크기·상한, 정렬 기준을 정한다. 화면이 어떤 데이터를 받아야 하는지도 응답 예시로 보여 준다.
- [ ] **07-API-02** 서버 입력 검증을 구현한다. 제목·본문·UUID·페이지 크기, 잘못된 JSON, 허용하지 않은 필드를 처리한다. 브라우저 폼 검증을 통과하더라도 서버는 다시 검사한다.
- [ ] **07-API-03** 목록·상세 GET API를 구현한다. 명시적인 정렬과 기본 페이지네이션을 적용하고 목록에는 필요한 컬럼만 반환한다. 없는 게시글과 읽을 수 없는 게시글의 응답 정책을 일관되게 적용한다.
- [ ] **07-API-04** POST API에서 서버가 검증한 사용자 ID를 작성자로 사용한다. 클라이언트가 보낸 `authorId`는 작성자 결정에 사용하지 않는다. 저장에 성공한 게시글의 ID와 화면에 필요한 값을 응답한다.
- [ ] **07-API-05** PATCH·DELETE API의 조건에 게시글 ID와 작성자 ID를 함께 넣는다. 존재 여부를 숨기는 경우 404를 반환하는 등 STEP 01의 정책을 따른다. 삭제 성공 응답과 반복 삭제의 처리도 명세에 적는다.

### 짧은 코드로 보는 API와 화면의 연결

```ts
// 서버 PATCH의 인가 핵심: 인증·입력 검증을 통과한 값만 사용한다.
const [updated] = await db
  .update(posts)
  .set({ title: newTitle })
  .where(and(eq(posts.id, postId), eq(posts.authorId, currentUserId)))
  .returning({ id: posts.id });

if (!updated) {
  return Response.json(
    { error: { code: "NOT_FOUND_OR_FORBIDDEN" } },
    { status: 404 },
  );
}
return Response.json({ data: updated });
```

첫 조건은 어떤 글을 바꿀지, 두 번째 조건은 누가 바꿀 수 있는지를 정한다. 화면에서 받은 ID만으로 UPDATE하면 다른 사람의 글을 바꿀 수 있으므로 두 조건을 함께 적용한다.

```ts
// 수정 폼의 제출 처리 일부. 서버가 성공했다고 응답한 뒤 이동한다.
const response = await fetch(`/api/posts/${postId}`, {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ title }),
});
const result = await response.json();
if (!response.ok) {
  setError(result.error.code); // 실제 화면에서는 사용자용 문구로 변환한다.
  return;
}
router.push(`/posts/${result.data.id}`);
router.refresh();
```

위 코드는 연결 지점을 설명하는 일부다. 실제 구현에는 import, 서버 인증·입력 검증·예외 처리, 폼의 네트워크 오류 처리·제출 상태 해제까지 포함한다. 프로젝트에서 정한 CSRF 방어도 함께 적용한다.

### JOIN을 사용하는 이유

```sql
-- $1에는 조회할 게시글 UUID를 바인딩한다.
SELECT c.id, c.body, c.parent_id, p.nickname
FROM comments AS c
JOIN profiles AS p ON p.id = c.author_id
WHERE c.post_id = $1
ORDER BY c.created_at ASC, c.id ASC
LIMIT 50;
```

댓글과 작성자 정보를 한 번에 읽는 예시다. 댓글마다 사용자 조회를 반복하는 구현과 쿼리 수를 비교한다. 실제 페이지네이션과 부모·자식 표시 방식은 UI 요구사항에 맞춘다. 화면은 이 응답의 `parent_id`로 정해진 관계를 표시하며, 서버가 거부한 관계를 임의로 생성하지 않는다.

### 두 가지 ID의 역할

| 값 | 해결할 문제 | 사용하는 위치 |
|---|---|---|
| `client_message_id` | 응답을 받지 못해 같은 전송을 재시도할 때 중복 저장 방지 | HTTP 작성 요청, DB UNIQUE, 기존 결과 반환 |
| 서버 `message.id` | 같은 메시지가 HTTP 응답·이력·이벤트로 여러 번 도착할 때 중복 표시 방지 | 화면의 이력·이벤트 병합과 렌더링 |

두 ID는 역할이 다르다. 서버가 저장한 결과를 먼저 기준으로 삼고, 화면에서는 그 결과와 실시간 전달을 합친다. 같은 재시도 키에 다른 본문을 넣었을 때의 처리도 API 계약으로 정의한다.

Supabase는 DB trigger 기반 Broadcast와 private channel의 권한 정책을 안내한다. 정책은 `realtime.messages`에 정의하며, 연결 중 접근 정책이 캐시되는 조건도 고려한다. [DB 변경 Broadcast](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes), [Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization).

`created_at, id`는 표시와 페이지네이션의 정렬 기준으로 사용할 수 있지만 DB 커밋 순서 자체를 뜻하지는 않는다. 증가하는 ID도 커밋 순서를 보장하는 근거로 사용하지 않는다. PostgreSQL의 `now()`는 트랜잭션 시작 시각을 반환한다. 따라서 마지막 시각 이후만 다시 읽는 단순한 구현을 근거 없이 무누락 복구로 설명하지 않는다. [PostgreSQL 시간 함수](https://www.postgresql.org/docs/current/functions-datetime.html).

### 실제 실행 계획을 읽는 예시

```sql
CREATE INDEX idx_messages_conversation_created
ON messages (conversation_id, created_at DESC, id DESC);

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, sender_id, body, created_at
FROM messages
WHERE conversation_id = $1
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

채팅방을 먼저 좁히고 그 안에서 최신 메시지를 정렬하는 조회를 위한 후보 예시다. `$1`은 실제 채팅방 UUID를 바인딩하거나 SQL Editor에서 개발용 값으로 대체한다. `EXPLAIN ANALYZE`는 쿼리를 실제 실행하므로 별도 측정 환경에서 실행한다. 이 예시 자체는 성능 개선의 증거가 아니며 실제 변경 전후 결과를 수집해야 한다. [복합 인덱스](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html).

## STEP 14 통합 테스트와 GitHub Actions CI 완성

**목표와 WHY:** 기능별 검증을 반복 가능한 자동 검사로 연결한다. 로컬 통과, CI 설정 작성, 원격 CI 통과는 다른 결과이므로 순서대로 확인한다. 테스트를 이 단계까지 미루지 않고 앞선 기능에서 만든 검증을 통합한다.

**선행 조건:** STEP 13 완료. **진행 상태:** `docs/work-status.md`에서 확인.

### A. 로컬 회귀 검증과 CI 설정

- [ ] **14-LOCAL-01** 지금까지의 단위·통합·E2E 검증을 요구사항과 대조한다. 중요한 정상·실패·권한·동시성·복구 시나리오의 누락을 찾는다.
- [ ] **14-LOCAL-02** Vitest·Playwright 설정과 실행 scripts를 정리한다. 현재 구성과 의미 있는 검증을 재사용하고 구현을 그대로 복사한 테스트나 낮은 위험의 문서 변경용 테스트를 늘리지 않는다.
- [ ] **14-LOCAL-03** 분리된 테스트 환경에 migration·seed·테스트 Auth 사용자를 준비한다. 실행별 상태 격리와 정리 방법을 확인하고 잘못된 DB 대상을 차단한다.
- [ ] **14-LOCAL-04** 로그인 후 게시글·댓글·친구·쪽지·채팅의 중요한 화면 흐름을 E2E로 연결한다. CI용 테스트 인증과 실제 Google OAuth 확인을 구분하고 운영용 인증 우회 경로를 만들지 않는다.
- [ ] **14-LOCAL-05** 입력·권한·롤백·동시성·채팅 재연결을 실제 환경에서 재검증한다. 실패한 핵심 검증을 단순 skip하여 성공으로 만들지 않는다.
- [ ] **14-LOCAL-06** `.github/workflows/ci.yml`에 lockfile 설치, 타입·린트·관련 테스트·빌드·필요한 E2E를 구성한다. 테스트 DB·브라우저 의존성·secrets의 준비 방법을 문서화한다.
- [ ] **14-LOCAL-07** 새 checkout 또는 이에 준하는 깨끗한 작업 환경에서 문서만으로 로컬 검증을 재현한다. 자동화된 범위·수동 확인·실행하지 못한 검증을 구분한다.
- [ ] **14-LOCAL-REVIEW** 사용자가 검증 범위, 실제 로컬 결과, CI 설정, 원격 실행에 필요한 준비를 확인하도록 제시하고 **멈춘다**. 아직 원격 CI를 실행한 것으로 기록하지 않는다.
- [ ] **14-LOCAL-COMMIT** 확인된 테스트·workflow·문서를 커밋하고 실제 해시를 기록한다. 이후 정해진 push 정책으로 원격 CI 실행을 준비한다.

### B. 외부 설정과 실제 CI 확인

- [ ] **14-CI-01** GitHub 저장소의 Actions 사용 가능 여부·secrets·variables·환경 권한을 확인한다. 직접 접근이 안 되면 저장소 Settings의 실제 화면과 입력할 변수명만 안내한다. 비밀값을 채팅으로 요구하지 않는다.
- [ ] **14-CI-02** 허용된 브랜치·push·PR 방식으로 workflow를 원격에 반영한다. 허용이 미정이면 실행할 대상과 영향이 구체적인 상태에서 필요한 확인을 받는다. 커밋 확인을 무관한 공개·배포 허용으로 넓히지 않는다.
- [ ] **14-CI-03** 실제 실행 이벤트에서 CI 결과·실패 로그·산출물을 확인한다. 수정이 필요하면 수정 범위를 로컬 검증→사용자 확인→커밋→허용된 push 순으로 처리하고 다시 CI 결과를 확인한다.
- [ ] **14-CI-04** 필수 검사의 실패가 병합을 막아야 한다면 저장소 ruleset·required status checks를 실제 권한과 지원 범위에서 설정·확인한다. workflow 파일만으로 병합 차단이 된다고 기록하지 않는다.
- [ ] **14-CI-REVIEW** 실제 run 주소·대상 커밋·성공/실패·병합 조건·남은 수동 검증을 제시하고 사용자의 확인을 **기다린다**.
- [ ] **14-CI-COMMIT** 확인된 운영 안내·검증 기록과 추가 수정이 있으면 해당 범위를 커밋한다. 기능 변경 없이 이미 커밋된 결과라면 기존 해시를 연결하고 불필요한 빈 커밋은 만들지 않는다. 다음 ID는 `15-PREP-01`이다.

## STEP 15 Vercel 배포와 운영 환경 구성

**목표와 WHY:** 로컬에서 확인한 API와 UI를 실제 환경에서도 확인한다. 저장소 연결·환경 변수·DB migration·OAuth 주소·배포·사용자 검수를 각각 나누어 문제의 위치를 찾는다.

- [ ] **16-03** 아키텍처·ERD·API 계약·화면 명세·인증·RLS 경계·트랜잭션·성능·테스트·배포 문서로 연결한다.

- [ ] **16-06** 핵심 경험별 1~2분 면접 답변과 꼬리 질문을 작성한다. 실제 코드를 설명하기 어려운 부분은 복습 항목으로 남긴다.
- [ ] **16-07** 새 방문자가 README로 실행·시연할 수 있는지 확인한다. 링크, 환경 변수 안내, 공개 범위, 데모 상태, API/UI 커밋 구분을 점검한다.
- [ ] **16-REVIEW** 사용자에게 README·화면·시연·문제 해결·남은 한계를 제시하고 최종 확인을 **기다린다**.
- [ ] **16-COMMIT** 확인된 문서·자료를 커밋하고 실제 해시와 최종 상태를 기록한다. push는 정한 정책을 따른다. 최종 응답에 실제 미완료·미검증·선택 보류를 남긴다.

**완료 기준:** 주장에 근거가 있고 방문자가 기능·화면·구현 이유·검증 범위를 이해할 수 있다. 실제 완료 수준과 문서가 일치한다.

**기본 개념:** ADR, 재현성, 기술적 의사결정, trade-off, 운영 한계.

**면접 질문:** “어려운 문제를 어떻게 발견했고 왜 그 방법으로 해결했나요?” 문제→원인→대안→선택→검증→한계를 실제 증거로 답한다.

**워크 요청:** `STEP 16을 진행해줘. 실제 API·UI와 검증 기록으로 포트폴리오를 완성하고 16-REVIEW에서 최종 확인 자료를 보여줘.`

## 사용자 확인 자료 양식

확인 자료는 `docs/reviews/<작업묶음>.md`처럼 찾을 수 있는 곳에 보관하고 진행 기록에서 연결한다. 빈 양식을 늘리는 대신 현재 묶음에 필요한 내용만 채운다. 아래는 형식 예시이며 실제 실행 결과가 아니다.

### API 확인 예시: 07-API-REVIEW

| 항목 | 작성할 내용 |
| --- | --- |
| 확인 범위 | 게시글 생성·목록·상세·수정·삭제 API와 권한·검증 |
| 접근 방법 | 실제 개발 서버 주소와 요청 실행 방법, A/B 로그인 준비 |
| 정상 시나리오 | A가 글 작성→ID 확인→상세 조회→수정→삭제 |
| 실패 시나리오 | 비로그인 작성, 빈 제목, B의 수정·삭제 요청 |
| 기대 결과 | 계약의 상태 코드·응답·DB 변화. 실패 시 DB 변경 없음 |
| 실제 자동 검증 | 실행한 명령·결과·환경·로그 위치 |
| 사용자가 볼 것 | 재현 요청·실제 응답·DB 결과와 코드의 핵심 WHY |
| 변경 범위·남은 문제 | 파일 목록, 알려진 제한, 미실행 검증 |
| 현재 상태 | 사용자 확인 대기, API 커밋 미수행 |
| 확인 뒤 작업 | 07-API-COMMIT → 07-UI-01 |

인증 API는 브라우저의 같은 출처에서 요청하거나 안전한 API 클라이언트 절차를 준비한다. 실제 세션 쿠키·토큰을 문서에 붙이지 않는다. 아래는 로그인한 개발 브라우저에서 확인할 요청의 모양이다. `POST`를 하기 전에 STEP 01 정책과 실제 API 계약·CSRF 방어에 맞는 절차를 준비한다.

```js
// 브라우저의 현재 앱과 같은 출처에서 목록 응답 확인
const response = await fetch("/api/posts?limit=5");
console.log(response.status, await response.json());
```

### UI 확인 예시: 07-UI-REVIEW

| 항목 | 작성할 내용 |
| --- | --- |
| 실제 접속 주소 | 사용자가 접근 가능한 목록·상세·작성 화면 URL |
| 역할·데이터 | 작성자 A, 다른 사용자 B, 확인용 글 |
| 클릭 순서 | A 로그인→작성→상세→수정→목록 확인→B로 접근 |
| 기대 화면 | 성공 후 목록·상세 갱신, 빈 제목 오류, 권한 표시 일치 |
| 상태 확인 | 로딩, 빈 목록, 요청 실패·재시도, 입력 내용 유지 |
| 기기·입력 확인 | 작은 화면·데스크톱·키보드로 주요 흐름 수행 |
| 실제 검증 | 관련 검사 결과, 실제 확인 화면, 미검증 항목 |
| 현재 상태 | 사용자 확인 대기, UI 커밋 미수행 |
| 확인 뒤 작업 | 07-UI-COMMIT, 요청 범위에 맞춰 다음 STEP |

### 사용자 응답과 재개 예시

```text
07 API 동작 확인했어. 해당 범위를 커밋하고 UI 구성과 API 연결을 진행해줘.
UI 확인 단계에서는 다시 멈춰줘.
```

```text
07 UI에서 저장 실패하면 입력 내용이 사라져. 그 부분을 수정하고 다시 확인할 수 있게 해줘.
아직 UI 커밋은 하지 마.
```

정해진 문구를 반드시 입력할 필요는 없다. 어떤 범위를 확인했는지가 분명하면 된다. 새 수정 요청을 받으면 변경 부분을 포함한 검증 자료로 같은 REVIEW를 다시 진행한다.

## 기록 예시와 기술적 결정

진행 기록의 실제 필드와 상태는 함께 제공하는 `docs/work-status.md`를 기준으로 한다. 확인 대기의 예시는 아래와 같다. 미리 완료 값이나 가짜 해시를 채우지 않는다.

```yaml
plan_revision: 2
current_step: "07"
current_unit: API
current_task_id: 07-API-REVIEW
status: WAITING_USER_REVIEW
verification: 실제 실행 결과와 증거 경로
user_review: 아직 확인받지 않음
commit_sha: null
next_task_id: 07-API-REVIEW
next_action: 사용자가 현재 API 확인
after_approval: 07-API-COMMIT
```

기술적 결정은 **문제 → 실제 원인 → 대안 → 선택과 WHY → 검증 → 결과와 한계** 순으로 남긴다. 예를 들어 친구 중복 관계 문제는 사전 조회, 사용자 쌍 정규화, UNIQUE, 트랜잭션이 각각 무엇을 해결하는지 설명하고 실제 동시 요청·롤백 결과를 연결한다.

| --- | --- |

| 환경·Git | 앱 경로, 실행 명령, 계정 인계, 연결 결과, commit·push 상태가 분명함 |
| API | 정상·입력·권한·실패·DB 영향의 실제 검증과 사용자 확인·커밋이 있음 |
| UI | 실제 API 연결, 화면별 동작·상태·반응형·키보드 검증과 사용자 확인·커밋이 있음 |
| 인증·인가 | 로그인·로그아웃·갱신, 타인 글·쪽지·채팅 접근 차단을 경로별 검증 |
| DB | 관계·제약·삭제 정책·migration·접근 제한을 재현 |
| 동시성 | 친구 수락 원자성, 중복 관계·방·메시지 처리 근거 |
| 실시간 | 참여자 구독, 중복 표시 방지, 검증 범위 내 복구와 명시한 한계 |
| 성능 | 비교 조건·원본 실행 계획·실측값, 화면 페이지 탐색 결과 |
| 품질·운영 | 실제 CI, 배포 URL·SHA, 로그·앱/DB 복구 절차 |
| 포트폴리오 | README에서 화면·코드·설계·검증·문제 해결 근거로 이동 |
| 진행 기록 | 사용자 확인·커밋·미완료·선택 보류·다음 행동을 사실대로 기록 |

선택 RBAC는 구현했을 때만 최종 검증에 포함한다. 목표는 사용한 기술 수보다, 만든 기능과 화면을 직접 확인하고 선택 이유와 검증 범위를 설명하는 것이다.
